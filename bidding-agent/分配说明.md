## 1. 仓库与协作流程（先做这个）

### 1.1 创建 origin（组长执行一次）



1. 组长在 GitHub 上新建**空仓库**（如 `bidding-agent`），**不要勾选** README /.gitignore（避免合并冲突）。

2. 在本地本目录执行：



```
git init -b main                      # 初始化仓库，默认分支 main

git add .

git commit -m "chore: 初始化项目骨架、参考文档与协作文档"

git branch -M main

git remote add origin https://github.com/<组织名>/bidding-agent.git   # 换成真实仓库地址

git push -u origin main
```



1. GitHub 仓库页面 → **Settings → Collaborators**，把另外 4 人添加为协作者（或邀请加入组织）。

### 1.2 5 人拉取与日常开发



```
\# 首次（每人）

git clone https://github.com/<组织名>/bidding-agent.git

cd bidding-agent

\# 建自己的功能分支（分支名建议与分工对应，见第 2 节）

git checkout -b feat/agent-core       # 例：成员 A

\# 日常循环

git pull origin main                   # ① 每天开工前同步 main

\# ... 开发、写测试 ...

git add .

git commit -m "feat(agent): 实现 ReAct 多轮循环的工具结果回填"

git push origin feat/agent-core        # ② 推送自己的分支

\# ③ 到 GitHub 页面发起 Pull Request（PR）→ 组长/队友 review → 合入 main
```

### 1.3 分支与合并规则（务必遵守）



| 规则           | 说明                                                                             |
| ------------ | ------------------------------------------------------------------------------ |
| `main` 是稳定分支 | **只有通过 PR 才能合入**，不在本地直接 push main（组长小修除外）                                      |
| 每人一条功能分支     | `feat/agent-core`、`feat/rag`、`feat/tools-data`、`feat/api-llm`、`feat/frontend`  |
| PR 要求        | 标题写明模块与改动（如 `feat(rag): ingest 支持多 Excel 合并`）；**CI 测试全绿** + 至少 1 人 review 后才合并 |
| 提交信息规范       | `类型(模块): 描述`，类型取 `feat / fix / docs / test / chore`；描述用中文，说明 "做了什么 + 为什么"      |
| 冲突处理         | 先 `git pull origin main` 在本地解决冲突 → 重新 commit → 再 push；不要用 `--force` 覆盖他人分支     |
| 合并方式         | 推荐 **Squash and merge**（一条 PR 一个提交，main 历史干净）                                  |

> 一条铁律：
>
> `.env`
>
> **&#x20;和密钥永远不入库**
>
> （
>
> `.gitignore`
>
>  已屏蔽；本地自行复制 
>
> `.env.example`
>
>  填写）。

## 4. 模块依赖与开发顺序



```
成员 B (RAG/数据管道) ──┐

&#x20;                       ├──→ 成员 A (Agent 核心) ──→ 成员 D (API/LLM) ──→ 成员 E (前端)

成员 C (工具/数据源) ───┘
```



* **阶段一（第 1–2 周，并行）**：全体搭环境（uv / npm / Qdrant / Neo4j / PostgreSQL，见 `docs/开发文档.md §2`）；**组长牵头冻结接口契约**（第 5 节）。B、C 先动（数据与数据源是地基）；A 设计 ReAct 循环（用 fake LLM 自测，见 `docs/开发文档.md §9.3`）；D 先搭 API 骨架与限流；E 先搭前端骨架与 SSE 解析。

* **阶段二（第 3–5 周，串行联调）**：A 接 B 的 `RAGPipeline` 与 C 的 `TOOL_EXECUTORS` → D 接 A 的 `chat_stream` → E 接 D 的 SSE 事件流；链路打通后补齐测试与评测。

* **阶段三（第 6–8 周）**：按第 7 节做二期功能增强 + 部署 + 文档与演示准备（完整排期见第 8 节）。

### 4.1 并行开发细则（重点，先读这条）

**联调顺序 ≠ 开发顺序**：上面的依赖图表示的是"谁需要谁的接口"，**不是**"等别人写完才能动手"。五人从第 2 天起并行开发，只有联调阶段才需要等上游模块落地。

1. **契约先行**：接口契约（工具返回 `{"success","data","error"}`、`RAGPipeline.search()` 签名、`TOOL_EXECUTORS` 注册方式、SSE 事件协议）在**阶段一**冻结于 `docs/开发文档.md §5/§6/§8`。B/C 还没写代码，A 也能照契约写调用方。
2. **mock 自测**：Agent 测试基建见 `docs/开发文档.md §9.3`——用文件内局部 fake 类（`_FakeLLM` / `ScriptedLLM`）模拟 LLM 与工具返回，不依赖真实数据源。A 的 react_loop / tool_text_parsing / sse_events / deep_thinking 测试从阶段一就能跑，不需要等 B/C。
3. **stub 先行**：B、C 尽早提交**接口骨架**（函数签名 + 返回结构 + 最小实现）到各自分支并合入 main，A clone 下来即可对着开发；B/C 随后在骨架内填真实实现，不影响 A。
4. **真正的等待点只有联调**：A 的端到端验证（真实检索、真实工具调用）从**阶段二** B/C 提交真实实现后才开始——**这一步**才需要"B/C 写完提交到远程仓库"。此前 A 的一切开发与单测都不依赖 B/C。

## 6. 测试、评测与文档义务



* **测试**：每人对自己模块写 pytest（mock 基建约定见 `docs/开发文档.md §9.3`，文件内局部 fake 类，monkeypatch 目标注意 `TOOL_EXECUTORS` 双处绑定）。**合入 PR 前&#x20;**`uv run pytest -q`**&#x20;必须全绿（目标 131 例）**，CI 会自动拦截。

* **评测**：`eval/ragas_eval.py`（RAG 质量）由 B 跑；`eval/agent_eval.py`（工具准确率）由 A 跑；`eval/dashboard.py`（运行看板）由 D 跑；E 负责前端与 SSE 联调验证。

* **文档同步**：改了什么就同步 `docs/开发文档.md` 对应章节（新增端点 / 配置项 / 包结构 / 工具都要登记），避免别人踩坑。

## 9. 常见问题速查



| 问题            | 处理                                                                              |
| ------------- | ------------------------------------------------------------------------------- |
| 启动即退出「缺少必需配置」 | `.env` 缺 QDRANT\_URL/QDRANT\_API\_KEY（或 deepseek key），对照 `docs/开发文档.md §2.3` 补全 |
| 首次问答极慢        | 嵌入 / 精排模型冷启动下载，等日志「模型预热完成」；离线可提前 `python main.py ingest` 触发                     |
| 检索结果质量骤降      | vocab.json 与向量数据不一致 → 更换数据后**必须重新 ingest**                                      |
| CI 红 / 测试不过   | `git pull origin main` 同步最新契约，本地复现修完再 push；不要绕过 CI 强合                           |
| PR 冲突         | 本地 `git pull origin main` 解决 → 提交 → push；绝不 `--force` 覆盖                        |
| 前端流式整段显示      | 生产环境 SSE 直连用 `NEXT_PUBLIC_API_BASE`；反代需 `proxy_buffering off`                   |
| 提交前最后自查       | `uv run pytest -q` 全绿；`.env` 未提交；密钥未进日志；相关文档已同步                                 |
