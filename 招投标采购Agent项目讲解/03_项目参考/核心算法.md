> 代码引用格式：`文件路径:函数/方法名`。流程图与机制说明见《组件工作机制.md》，配置与排障见《开发文档.md》。

## 1. 检索链路总览

```
用户问题
  ├─ ① 问题分类            → keyword / concept / mixed（决定 RRF 参数）
  ├─ ② 双路编码            → Dense (BGE 512维) + Sparse (BM25)
  ├─ ③ Qdrant 混合召回     → Prefetch 双路各 30 条 + RRF 融合
  ├─ ④ CrossEncoder 精排   → 召回结果重打分取 top-k (默认 5)
  └─ ⑤ LRU 缓存            → (question, top_k) → 结果, 128 条
```

## 2. 问题分类与 RRF 参数选择

**位置**：`src/rag/vector_store.py:_classify_question` / `_rrf_k_for`

### 2.1 词表

| 类型 | 词表 | 示例 |
|---|---|---|
| 关键词 `_KEYWORD_TERMS` | 法规、招标、投标、采购、合同、质疑、投诉、限额、标准、规定、条件、流程、期限、罚款、责任 | 精确检索型意图 |
| 概念词 `_CONCEPT_TERMS` | 什么、如何、为什么、区别、对比、比较、分析、评估、建议 | 语义泛化型意图 |

### 2.2 判定规则（伪代码）

```
kw = 命中关键词表的个数
cp = 命中概念词表的个数
if kw >= 2:            return "keyword"    # 阈值 MIN_KEYWORD_HITS
if cp >= 2 and kw == 0: return "concept"    # 概念型要求完全无关键词
return "mixed"
```

### 2.3 设计要点

- **阈值 ≥2 而非 ≥1**：单个词（如「如何」或「招标」）在混合型问题中出现率高、噪音大，需要 ≥2 个同类型词相互佐证
- **concept 要求 kw == 0**：只要混入一个关键词就按 mixed 处理（检索参数取均衡值更稳妥）
- 未命中任何词（如「随便说说」）与空串 → mixed

### 2.4 RRF k 映射

| 类型 | k 值 | 效果 |
|---|---|---|
| keyword | 30 | 偏重 Sparse（BM25 关键词精确匹配），排名靠前的结果权重被放大 |
| concept | 90 | 偏重 Dense（语义泛化），多路结果更均衡 |
| mixed | 60 | 默认均衡 |

## 3. BM25 稀疏编码（SparseEncoder）

**位置**：`src/rag/embedder.py:SparseEncoder`

### 3.1 离线拟合（ingest 时）

```
fit(documents):
  对每个文档: tokens = jieba 精确模式分词, 过滤长度 ≤1 的词
  统计每个 token 的文档频率 df
  词汇表 = 按 df 降序排列的 token 列表（常见词在前, 索引小）
  IDF(token) = ln( (N - df + 0.5) / (df + 0.5) + 1 )      # N = 文档总数
  落盘 data/vocab.json（查询端加载, 必须与向量数据同源）
```

### 3.2 在线编码

```
encode(text):
  tokens = jieba 精确模式分词, 过滤单字
  tf  = Counter(tokens); total_terms = len(tokens)
  对每个 token (在词表中):
    tf_norm  = count / total_terms                        # 归一化词频
    weight   = IDF(idx) × ((k1 + 1) × tf_norm) / (k1 + tf_norm)    # k1 = 1.2
  按索引升序排序 → {"indices": [...], "values": [...]}
```

### 3.3 关键参数与边界

| 项 | 值/处理 |
|---|---|
| k1 | 1.2（词频饱和因子） |
| 分词 | jieba `lcut` 精确模式；过滤单字与空白 |
| OOV 词 | 直接跳过（不在词表中不计入向量） |
| 空 token 集 | 返回 `{indices: [], values: []}` |
| **一致性约束** | 查询与文档必须用**同一份 vocab.json**；换数据必须重新 ingest，否则词表/维度错位 |

## 4. Dense 语义编码（BGE）

**位置**：`src/rag/embedder.py:Embedder`

```
encode_query_dense(q):    SentenceTransformer.encode(BGE_QUERY_PREFIX + q, normalize_embeddings=True)
encode_document_dense(d): SentenceTransformer.encode(d, normalize_embeddings=True)
```

- 模型：`BAAI/bge-small-zh-v1.5`，输出 512 维，L2 归一化（配合 Qdrant COSINE 距离）
- **查询必须带指令前缀**（`为这个句子生成表示以用于检索相关文章：`），文档不带——BGE 系列的非对称使用约定，直接影响召回质量
- 懒加载 + 双重检查锁：并发首次使用只加载一份模型；`torch.OutOfMemoryError` 时降级 CPU 重载

## 5. RRF 混合融合

**位置**：`src/rag/vector_store.py:VectorStore.hybrid_search`

### 5.1 流程（伪代码）

```
hybrid_search(query_dense, query_sparse, limit, dense_limit=30, sparse_limit=30, question):
  k = _rrf_k_for(question)
  response = query_points(
    prefetch = [ Prefetch(dense,  limit=30),
                 Prefetch(sparse, limit=30) ],
    query    = RrfQuery(rrf=Rrf(k=k)),
    limit    = limit, with_payload=True)
  return [ {id, score, question, answer} for hit in response.points ]
```

### 5.2 RRF 打分公式

```
RRF(d) = Σ_{每路检索} 1 / (k + rank_i(d))
```

- `rank_i(d)`：文档 d 在第 i 路（dense/sparse）结果中的排名（从 1 起）
- 文档只在一路出现时，另一路贡献为 0
- k 越大，低排名文档权重衰减越慢（多路融合越均衡）

### 5.3 召回上限

`rag_pipeline._search_no_cache` 取 `recall_limit = max(top_k × 6, 30)`，即 top_k=5 时召回 30 条交给精排。

### 5.4 容错

`_retry_call` 对 `ResponseHandlingException` 重试 2 次（间隔 1s），最终失败返回空列表（上层按「未检索到」处理，不崩溃）。

## 6. CrossEncoder 精排

**位置**：`src/rag/embedder.py:Reranker.rerank`

```
rerank(query, docs, top_k):
  if len(docs) <= 1: return docs                    # 单条无需精排
  pairs = [(query, doc["answer"]) for doc in docs]  # 与答案文本配对
  scores = model.predict(pairs)                     # bge-reranker-base
  将分数写回各 doc["score"], 按降序排序
  return docs[:top_k]
```

- **配对对象是 answer 而非 question**：知识库点以「答案」为文档主体（dense 编码也是 answer），评分口径一致
- 精排只对初检结果打分（交叉编码器对 (query, answer) 对逐对计算，成本高，不能全库扫）

## 8. ReAct 多轮推理循环

**位置**：`src/agent/react_loop.py:_chat_stream_tools`

### 8.1 循环结构（伪代码）

```
MAX_TOOL_ROUNDS = 4
for round_idx in 1..4:
    if round_idx > 1: yield status「正在分析检索结果...」   # 观察轮提示
    response = llm.chat_raw(messages, tools=active_tools, ...)
    if 异常:
        if round_idx == 1: 降级 _fallback_rag（纯知识库路径）; return
        else: 追加 _CAP_CONSTRAINT_TEXT; break            # 不丢弃已收集结果
    choice = response.choices[0]
    if choice.message.tool_calls:                          # ① 原生工具调用
        归一化 content → 并行执行 → 回填 tool 消息 → continue
    else:
        raw = content 或 reasoning_content 回退
        if _parse_text_tool_calls(raw) 解析出有效调用:      # ② 文本工具调用兜底
            执行 → 结果以 user 消息回填 → continue
        if raw 干净且不像工具格式: answer = raw; break      # ③ 任意轮直答
        break                                              # ④ 空/疑似格式 → 最终生成兜底
else:                                                      # for 自然耗尽 = 4 轮全是工具轮
    追加 _CAP_CONSTRAINT_TEXT
# 循环出口
if answer 为空: _clean_for_final 重建消息 → 流式最终生成
else:          直答内容按小帧流式输出
```

### 8.2 退出条件矩阵

| 条件 | 动作 |
|---|---|
| 首轮 LLM 异常 | 降级 RAG / error 帧，`return` |
| 第 N≥2 轮 LLM 异常 | 上限约束 → `break` → 基于已有结果最终生成 |
| 有工具调用（原生/文本兜底） | 执行 + 回填 → `continue` |
| 干净直接回答（任意轮） | 直答流式（不再多一次 LLM 调用） |
| 疑似格式解析不出 / 空内容 | `break` → 最终生成兜底 |
| 4 轮全部是工具轮 | `for...else` 触发上限约束 → 强制最终生成 |

### 8.3 关键设计

- **`for...else` 语义**：`break`（正常退出）跳过 `else`；只有 4 轮全部 `continue` 才触发上限约束——无需额外标志位
- **上限约束文案** `_CAP_CONSTRAINT_TEXT`：「必须立即基于以上所有工具结果直接回答…禁止再调用任何工具」，同时用于循环中途 LLM 失败场景
- **思考模型每轮省略 `tool_choice`**（DeepSeek 推理模型对该参数返回 400；省略即 auto 语义）
- **阶段计时**：`t_first`（首轮 LLM 完成）、`t_tools`（每轮工具执行完成时更新）→ phase_times 的「首轮分析 / 检索与搜索 / 生成回答」三阶段自然涵盖全部轮次

## 9. 最终消息重建（_clean_for_final）

**位置**：`src/agent/react_loop.py:_clean_for_final`

```
输入: messages（含 system/history/question + 多轮工具回合）, question, tool_msgs_start
输出: [system, user(question), ...按原始顺序的工具回合..., system(最终约束)]
```

- **顺序保持**：单次顺序遍历 `messages[tool_msgs_start:]`，`tool` 消息紧跟其前导 `assistant(tool_calls)`——OpenAI 协议要求 tool 消息紧随其 assistant，两遍收集（先全部 assistant 再全部 tool）会压平多轮交错
- **归一化**：SDK 对象（assistant.message/tool_calls）转为纯 dict，防历史遗留的 str() 化消息（`ast.literal_eval` 防御分支）
- **user 消息按序保留**：文本兜底回填消息与上限约束消息位于对应结果之后，重建后顺序天然正确（此前实现丢弃这些消息，导致文本兜底路径最终生成看不到检索结果——已修复）
- **尾部约束**：「只能使用上面工具返回的检索结果…禁止编造…只输出纯文本」，隔离最终回合防幻觉

## 11. 工具调用文本检测

**位置**：`src/agent/tool_defense.py:_looks_like_tool_call`

### 11.1 检测策略（全文本子串，非只看开头）

```
1. DSML 组合检测: "<【" in low and "dsml" in low
   → 覆盖流式分块把 "<【" 与 "dsml" 拆开的情况（单独 "<【" 不算）
2. 开头快速路径: low.startswith("<") 或 "{" 且前 200 字符含
   tool_call / invoke / function_call / "name" 任一
3. 全文本子串匹配（模型常「正文 + 工具调用块」混出）:
   "<tool"（不带后缀, 覆盖缓冲边界把 "<tool" 与 "call>" 拆开）
   "<invoke" / "<function_call"
   '"name": "search_' / '"function": {"name"'
   "search_bidding_knowledge(" / "search_knowledge_graph(" /
   "search_postgresql(" / "search_web(" / "search_exa("
```

### 11.2 设计要点

- 覆盖三种格式族：XML（`<tool_calls>/<invoke>`）、OpenAI JSON（`function: {name}`）、**DSML**（DeepSeek 的 `<【DSML】tool_calls>` 标记）
- 开头匹配会漏检「正文 + 工具块」混合输出（曾导致工具文本泄漏给用户），故用全文本子串
- 检测仅用于**防御**（缓冲拦截 + 兜底解析前置判断），不追求零误报：疑似即拦截，代价只是一次约束重试

## 12. 文本工具调用解析

**位置**：`src/agent/tool_defense.py:_parse_text_tool_calls`

三个正则风格依次尝试（任一命中即追加）：

| 风格 | 模式 | 容错 |
|---|---|---|
| XML/DSML invoke | `<invoke name="X"><parameter name="k">v</parameter>...` | **invoke 块允许不闭合**（lookahead 到下一个 invoke/容器尾/串尾）；支持 `【DSML】` 前缀 |
| XML tool_call 块 | `<tool_call><name>X</name><k>v</k>...</tool_call>` | `name` 标签缺失则跳过该块；参数标签任意键名（排除 name） |
| JSON | `{"name": "search_xxx", "arguments": {...}}` | `json.loads` 失败（非严格 JSON）则跳过该项；arguments 非 dict 忽略 |

- 返回 `list[{name, arguments}]` 或 `None`（解析不出任何调用）
- 上游过滤：`valid_calls = [c for c in parsed if c["name"] in TOOL_EXECUTORS]`，只执行白名单内工具
- 执行时构造 `SimpleNamespace` fake tool_calls 走与原生调用**完全相同的**执行管线（含质量标签、来源收集）

## 13. 流式防泄漏缓冲与约束重试

**位置**：`src/agent/generation.py:_generate_stream / _generate_deep`

### 13.1 缓冲状态机

```
pending = ""                                   # 未 flush 缓冲
for text in llm.chat_stream(...):
    pending += text
    if _looks_like_tool_call(pending):         # 缓冲内检出
        yield reset                              # 前端清空已流正文
        追加约束 user 消息（"禁止输出 <tool_call>、JSON 函数调用或任何 XML 标签…"）
        yield 非流式 _generate 重试结果          # 走 3 次重试
        return
    if len(pending) >= STREAM_FLUSH_CHARS(80):
        按小帧 flush pending; pending = ""
# 流结束
flush 剩余 pending
answer = join(所有已 flush 片段)
if answer 为空: 兜底提示
if _looks_like_tool_call(answer):              # 全量兜底检测（缓冲边界可能拆开 "<tool" 与 "call>"）
    同样 reset + 约束重试一次
```

### 13.2 设计要点

- 检出模式含 `<tool` 前缀，**工具块开头在任何阈值下都会落在缓冲内被拦截**（不会被 flush 出去）
- 双层检测：缓冲层（增量时）+ 全量层（流结束时），覆盖边界拆分漏检
- 重试失败极限：`_generate` 3 次尝试均返回工具格式 → 降级回答「抱歉，生成回答时出现技术问题」，绝不输出工具文本
- 深度思考模式（`_generate_deep`）同构：`chat_stream_thinking` 的 thinking 增量直接透传，content 增量走同一缓冲；缓冲检出时 `content_parts.clear()` + reset

## 15. 联网结果相关性重排

**位置**：`src/tools/rag_tools.py:_rerank_web_results`

```
输入: question, items=[{question, answer, score, url}, ...]
1. len < 2 → 原样返回（单条保留引擎自带分）
2. 构造 docs = [(用户问题, 结果标题+正文)], 携原始下标 _i
3. reranker.rerank(question, docs, top_k=len) → 分数写回各 item["score"]
4. 按分数降序排序
5. 归一化 min-max 到 [0, 1]:
   x' = (x - min) / (max - min)     当 max > min
   x' = 1.0                         当 max == min 且 > 0（全同分视为全相关）
   x' = 0.0                         当 max == 0
6. 重排失败（模型未加载/离线）→ 原样返回引擎分, 仅告警日志
```

- 原始 logits 不可直接当百分比展示，归一化后前端按百分比渲染
- **与用户问题**计算相关性（而非与检索查询）——保证多工具并行时评分口径一致

## 17. 滑动窗口限流

**位置**：`src/rate_limiter.py:RateLimiter`

```
is_allowed(client_id):
  now = time(); window_start = now - 60
  加锁:
    每 300s 清理一次无活跃请求的客户端条目（防内存膨胀）
    该客户端时间戳列表 = [t for t in 列表 if t > window_start]     # 滑出窗口的丢弃
```

## 20. PostgreSQL 双向模糊匹配与 LIKE 转义

**位置**：`src/database/postgresql_client.py`

### 20.1 LIKE 转义（_escape_like）

```
value.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")
配合 SQL 端 ESCAPE '\'
```

关键词中的 `%`/`_` 不加转义会被当通配符（如关键词「100%」会匹配所有含「100」的文本）；反斜杠最先转义。

### 20.2 双向匹配（search_by_keyword / filter_by_field）

```
正向: WHERE 字段 ILIKE '%关键词%' ESCAPE '\'
反向: 正向无结果 且 len(关键词) >= 3 时
      WHERE char_length(字段) >= 3 AND 关键词 ILIKE '%' || 字段 || '%'
```

- 解决的问题：LLM 传入的关键词常是实际名称的**超集**（如带「招标公告」后缀），正向匹配落空；反向匹配让「关键词包含字段值」也能命中
- 反向仅对 `title`/`project_name`（采购人/供应商反向匹配噪音大）；`char_length >= 3` 过滤超短字段值导致的全表噪音

## 21. 工具并行执行与超时隔离

**位置**：`src/tools/base.py:ToolRunner.run_parallel`

```
ThreadPoolExecutor(max_workers=4) 提交所有合法调用
as_completed(pending, timeout=30):
  完成 → ToolResult(文本, sources)
  异常 → ToolResult(「执行失败: e」)
TimeoutError → 未完成的全部返回「执行超时(>30秒)」
finally: pool.shutdown(wait=False, cancel_futures=True)
```

- 未知工具 / 参数 JSON 解析失败：直接生成失败文本 ToolResult（保证每条 assistant(tool_calls) 都有对应响应，协议完整）
- **Python 线程无法强制终止**：超时的工具线程在其内部调用自行结束后退出——因此 Qdrant 30s / Neo4j 事务 30s / MCP 60s 均已在源头配置超时兜底
- 失败文本作为 tool 消息回填给 LLM，让其据此降级回答（Agent 永不因死后端崩溃）

## 22. MCP 客户端协议机制

**位置**：`src/mcp/mcp_client.py:McpClient`

| 机制 | 实现 |
|---|---|
| 传输 | stdio JSON-RPC 2.0，行分隔（一行一请求/响应） |
| 握手 | `initialize`（protocolVersion `2024-11-05`）→ `notifications/initialized` → `tools/list` |
| 串行化 | 全局锁：请求 ID 自增与 stdin 写入必须原子（工具并行会共享客户端） |
| 读超时 | 每次 `_recv` 起守护 reader 线程 + `queue.get(timeout=60)`，超时抛 TimeoutError（不依赖线程强制终止） |
| stderr 排空 | 守护线程持续读服务器 stderr 到日志——不读会写满 64KB 管道缓冲区死锁 |
| 崩溃自愈 | 进程 `poll()` 检出退出 → 自动重启；**30s 重启限频**（启动即崩溃的服务器如无效 API key 不会被每个请求反复拉起） |
| 平台适配 | Windows 上 `npx` → `npx.cmd`，`shell=True` |

## 24. 前端算法

### 24.1 流式状态机防护（frontend/app/page.tsx）

三重校验防止旧流错写新会话：

| 防线 | 机制 |
|---|---|
| 取消 | `AbortController`：发送新请求/切换会话/新建会话时 abort 进行中的流 |
| 序号 | `requestSeqRef` 递增序号：流结束收尾前校验仍是最新请求，否则结果作废 |
| 归属 | `sessionIdRef`：保存前校验消息属于发起时的会话，防止切换会话后旧流错存 |

SSE 解析：逐行处理，仅 `data: ` 前缀行；单行 JSON 失败不中断整个流；流结束未收到 done/error → 兜底「连接中断」；异常时保留已流正文并附加「回答可能不完整」。

### 24.2 图片压缩（components/ChatInput.tsx）

```
原始文件 ≤ 10MB（超限直接拒绝）
canvas 压缩: 长边缩放至 ≤ 1024, 输出 JPEG quality 0.85
透明 PNG → 先铺白色背景（避免 JPEG 黑底）
```

## 25. 检索质量标签（_validate_result）

**位置**：`src/agent/react_loop.py:_validate_result`

```
has_data = 文本非空 且不含「未找到/未返回/失败」
按工具类型附加标签:
  search_bidding_knowledge: 无 sources → ⚠️ 未检索到相关文档
                           有 → 均分 ≥ 0.5 ? ✅ 检索质量良好 : ⚠️ 相关性偏低（含条数与均分）

无标签且无数据 → ⚠️ 工具返回空结果
```

- `✅/⚠️` 前缀不进入用户正文（前端按 sources 渲染，标签仅供生成参考）
