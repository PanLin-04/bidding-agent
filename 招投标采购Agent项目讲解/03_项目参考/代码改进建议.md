# 代码改进建议

> 审查日期：2026-08-13
> 审查范围：`src/`（Agent、RAG、客户端、数据库、工具、MCP）、`api/`、`frontend/`（Next.js 14）、`batch/`、`eval/`、`main.py`、`pyproject.toml`
> 审查方式：逐文件精读 + 两个并行子代理交叉审查（前端 24 项、批量/评测脚本 19 项），关键疑点已运行验证

## 总体评价

项目整体架构清晰：模块划分合理（client / tool / database 分层）、单例懒加载模式统一、SQL 全参数化并带字段白名单、SSE 协议前后端匹配良好、react-markdown 未装 rehypeRaw 因此 XSS 面基本可控。主要风险集中在四类：

1. **超时与异常隔离缺失**——工具执行、MCP 子进程、LLM 生成任一环节挂起或抛异常，都会拖死或截断整个请求；
2. **流式对话的边界状态**——前端切会话/断流时无 AbortController，可能损坏已保存的会话数据；
3. **批量脚本的数据安全**——原地覆盖源文件、空键行误合并、坏行整体崩溃；
4. **评测与生成管道不一致**——评测的 contexts 不是生成回答实际使用的文档。

## 一、高优先级：正确性与数据安全（建议优先修复）

### 🔴 1. 工具执行无超时、无异常隔离

> ✅ **已实施（2026-08-13）**：`ToolRunner.run_parallel` 加 30s 总超时与 per-tool 异常隔离（`TOOL_TIMEOUT_SECONDS`，未知工具/坏参数也返回 tool 消息）；`McpClient` 加守护线程排空 stderr、响应读取超时（默认 60s）、请求配对加锁、握手失败终止进程；Neo4j `_run` 改用 `session.begin_transaction(timeout=30)`。已用假工具验证 5 条路径（成功/异常/超时/未知工具/坏参数）与 MCP 握手超时。

- **位置**：`src/tools/base.py:72-80`、`src/mcp/mcp_client.py:28-32, 68-70`
- **问题**：
  - `ToolRunner.run_parallel` 中 `future.result()` 无 timeout、无 try/except。Qdrant/Neo4j/PostgreSQL/Tavily/Exa 任一环节挂起（如 Neo4j `session.run` 无查询超时），整个请求永久等待；任一工具抛异常，SSE 流直接中断。
  - `McpClient._recv()` 用 `readline()` 无超时，Exa MCP Server 无响应时线程永久阻塞。
  - `subprocess.Popen` 指定 `stderr=PIPE` 但从不读取——服务器 stderr 写满 64KB 管道缓冲区即死锁（经典 subprocess 死锁）。
- **建议**：
  - `run_parallel` 中为每个 future 加 `result(timeout=30)`，单工具 try/except，失败时把错误文本作为该 tool 消息返回给 LLM（而不是整体崩溃）；
  - MCP stderr 重定向到 `subprocess.DEVNULL` 或用守护线程排空；`_recv` 加超时；
  - Neo4j 查询加 `transaction_timeout` 或 `session.run(..., timeout=...)`。

### 🔴 2. LLM 生成/工具执行异常逃逸，流截断时无 error 事件

> ✅ **已实施（2026-08-13）**：后端 `chat_stream` 主体提取为 `_chat_stream_tools` 并用最外层 try/except 兜底——`_get_llm` 失败、工具执行/最终生成任何未捕获异常都以 `error` 事件结束（不再截断）；顺带把两处重复的 `evt` 闭包统一为模块级 `_sse()`。前端流循环跟踪 `finished` 标志（done/error 到达置位），流结束但未收到两者且 answer 为空时显示"连接中断，请重试。"；`:189` 静默 `catch {}` 改为 `console.warn` 记录解析失败行。已用假 LLM 验证 3 条路径（正常 done / 工具异常 error / LLM 初始化异常 error），前端 `tsc --noEmit` 通过。

- **位置**：`src/agent.py:404-439`；前端 `frontend/app/page.tsx:166-202`
- **问题**：`chat_stream` 中 `runner.run_parallel`（:411）和 `_generate`（:433）都不在 try 内，异常时生成器直接终止——前端 `reader.read()` 正常返回 done，但既无 `done` 也无 `error` 事件，最终渲染**空内容的助手消息且无任何报错**；`page.tsx:189` 的 `catch {}` 又静默吞掉 JSON 解析错误（如 `data: [DONE]`）。
- **建议**：`chat_stream` 最外层包 try/except，任何异常都 `yield evt("error", ...)`；前端流结束时校验：未收到 `done`/`error` 且 answer 为空时，显示"连接中断，请重试"兜底提示。

### 🔴 3. 流进行中切换/新建对话会损坏会话数据

> ✅ **已实施（2026-08-13）**：`chatWithAgentStream` 增加 `signal` 参数直通 fetch。`page.tsx` 每次发送创建 `AbortController`（`abortRef`），新建/切换/清空对话时 `abort()` 取消旧流；新增 `requestSeqRef` 请求序号——流结束收尾、catch、finally 均先校验序号，旧流不会覆盖新会话消息、不会复位新请求的 loading；保存前用 `sessionIdRef` 校验会话归属（`sendSessionId === sessionIdRef.current`），切换后跳过保存；`saveConversation` 副作用移出 `setMessages` updater（避免 StrictMode 双调用重复保存），最终列表由本地 `currentMessages + assistantMsg` 组装而非依赖可能被清空的 `prev`。前端 `tsc --noEmit` 通过。

- **位置**：`frontend/app/page.tsx:208-221, 233-251`
- **问题**：`chatWithAgentStream` 无 AbortController，切会话时旧流继续跑；流结束时 `setMessages` updater 内的 `saveConversation` 使用闭包里的旧 `sessionId` 和已被清空的 `prev`，结果把**空消息覆盖写入旧会话**并重设标题。切会话/新建对话均无防并发保护。
- **建议**：每次发送创建 `AbortController`，切换/新建会话时 `abort()` 取消旧流；保存前校验 `currentSessionId` 与消息归属是否一致。

### 🔴 4. 流中断丢失已流式渲染的内容

> ✅ **已实施（2026-08-13）**：`streamedContent` 提升到 try 外声明（catch 块访问不到 try 内的 let）；异常时若有已流式内容，保留为助手消息正文并附加 `> ⚠️ 错误原因（回答可能不完整）` 提示，同时经 `persistConversation` 持久化（否则切会话后部分内容仍会丢失）；无任何已流式内容时才移除占位消息并走错误横幅。网络层错误（`Failed to fetch`/`NetworkError`）统一映射为中文"网络连接中断"。前端 `tsc --noEmit` 通过。

- **位置**：`frontend/app/page.tsx:222-225`
- **问题**：网络错误/代理断开/后端异常时，catch 直接删除 thinking 消息，**已经流式显示的部分回答全部丢失**。
- **建议**：保留已流式内容作为消息正文，错误以附加提示形式展示。

### 🔴 5. 多轮对话反馈归属错误

> ✅ **已实施（2026-08-13）**：`ChatContainer` 的消息映射改为带索引遍历，助手消息从 `idx-1` 向前找**紧邻的前一条 user 消息**作为 `userQuestion`（向前循环兼容非严格交替的消息列表），纯图片消息以 `imageName` 兜底避免空问题；不再取整个列表最后一条 user 消息。前端 `tsc --noEmit` 通过。

- **位置**：`frontend/components/ChatContainer.tsx:67`（消费方 `ChatMessage.tsx:38`）
- **问题**：`userQuestion` 取整个消息列表**最后一条** user 消息传给所有助手消息——多轮对话中第 1 条回答的点赞/点踩会错误归属到后续轮次的问题。
- **建议**：每条助手消息取**紧邻其前一条** user 消息作为反馈上下文。

### 🔴 6. `crypto.randomUUID` 在非安全上下文不存在

> ✅ **已实施（2026-08-13）**：`page.tsx` 模块级新增 `generateId()` —— `crypto.randomUUID` 可用（安全上下文）则用之，否则降级为 `时间戳(36进制) + 随机数`；启动加载与切换会话两处 `m.id || crypto.randomUUID()` 均替换为 `generateId()`，局域网 IP/容器 HTTP 部署下历史对话不再静默加载失败。前端 `tsc --noEmit` 通过。

- **位置**：`frontend/app/page.tsx:89, 246`
- **问题**：该 API 仅在 HTTPS/localhost 下可用；局域网 IP 或容器 HTTP 部署时 `crypto.randomUUID` 为 undefined，抛 TypeError 被 `.catch(() => {})` 吞掉 → 历史对话**静默加载失败**。
- **建议**：提供降级 ID 生成器（时间戳 + 随机数）。

### 🔴 8. 数据导入时 NaN 变成字符串 "nan" 混入知识库

- **问题**：`df["question"].astype(str)` 把 NaN 转成 `"nan"`，`!= ""` 过滤不掉——question 为空、answer 有效的行全部通过过滤，以问题 `"nan"` 导入向量库（已实际验证）。
- **建议**：先用 `dropna(subset=["question", "answer"])` 或 `notna()` 过滤。

### 🔴 9. 批量脚本：坏行崩溃 + 空文件 IndexError

> ✅ **已实施（2026-08-13）**：解析失败的坏行**跳过并计数报告**（不再"原样追加"进输出）；解析阶段把 `custom_id` 随行保存（`(key, cid, line)` 三元组），验证循环直接复用、不再二次 `json.loads`（坏行不可能再让脚本崩）；空文件/全部坏行时打印警告并提前 `return 0`（不再触 `sorted_ids[0]` IndexError）；保存日志显示实际写入行数。已用临时目录实测 3 场景：坏行+乱序（跳过 1 行、排序 request-1→3、输出 3 行原始内容）、空文件（警告 + 退出码 0）、输出内容与源行逐字节一致。

- **位置**：`batch/按custom_id排序.py:62, 70, 83`
- **问题**：:62 对解析失败的行打日志"原样追加"，但 :70 的验证循环对每行再次 `json.loads` 且无异常处理，坏行直接抛 JSONDecodeError 终止整个脚本；文件为空时 :83 `sorted_ids[0]` 抛 IndexError。
- **建议**：坏行跳过并计数报告；空文件提前 return。

### 🔴 10. 批量脚本：原地覆盖源 Excel，无备份

- **位置**：`batch/提数据_插标的物.py:130`

### 🔴 11. 去重脚本：空键行被错误合并，可能误删数据

> ✅ **已实施（2026-08-13）**：移除 `"__NULL__"` 字符串哨兵（fillna/replace 全删）——`drop_duplicates` 中 NaN 键天然视为相等，无需哨兵；键全为空的行（`isnull().all(axis=1)`）单独分离、不参与去重分组、最后按原始索引合并还原行序；重复统计同步排除空键行且 `groupby(dropna=False)` 保持 NaN 键分组计数准确；顺带修复了哨兵导致的 `中标金额` 列退化为 object dtype 的问题（现保持数值型）。已用构造数据验证：2 条空键不同内容行全部保留、同组空值多的行被正确淘汰、真实 `"__NULL__"` 字符串不再被替换为 NA。

- **位置**：`batch/去重.py:44-45, 63-64, 71`
- **问题**：项目编号和中标金额均为空的行归入同一个 `("__NULL__","__NULL__")` 组被去重合并成 1 行——内容不同的合法记录被删除；若真实数据恰好含字符串 `"__NULL__"` 会被误替换为 pd.NA。
- **建议**：空键行不参与去重分组；用 NaN/None 而非字符串哨兵。

### 🔴 12. 评测上下文与生成上下文不一致，Faithfulness 失真

> ✅ **已实施（2026-08-13）**：`ask()` 不再自行编码 + `hybrid_search`，改为直接复用 `self.search(question, top_k)`——hybrid 召回 + CrossEncoder 重排 + LRU 缓存同一套管道。评测脚本（`ragas_eval.py`/`agent_eval.py`）用 `search()` 生成的 contexts 与 `ask()` 实际生成 answer 使用的文档完全同源，Faithfulness/Recall 不再失真；顺带 `/api/ask` 也获得检索缓存收益。已用打桩 `search`/`generate_answer` 验证调用链 `ask → search(question, top_k)`、answer 与 sources 均来自重排后文档。

- **位置**：`eval/ragas_eval.py:99-102`、`eval/agent_eval.py:57-59`；根因 `src/rag_pipeline.py:68-96`
- **问题**：评测用 `search()`（走 rerank，:53-54）生成 contexts，但 `ask()` 内部直接用 `hybrid_search` 结果生成回答（**无 rerank**）——评测的 contexts 不是生成 answer 实际使用的文档，Faithfulness/Recall 分数失真。
- **建议**：让 `ask()` 复用 `search()` 的结果（或统一两条管道），保证评测与线上生成同源。

### 🔴 13. 后端 async 端点内执行阻塞调用

> ✅ **已实施（2026-08-13）**：11 个纯阻塞端点全部由 `async def` 改为普通 `def`——`/api/health`、`/api/chat`、`/api/ask`、`/api/chat/stream`、`/api/conversations`（5 个 CRUD）、`/api/feedback`、`/api/vision`，并在路由区加注释说明。FastAPI 自动将 def 端点放入线程池（AnyIO worker thread）执行，慢请求（LLM 生成数十秒）不再阻塞事件循环、限流中间件与健康检查。已用 TestClient 打桩验证：/api/chat、/api/ask、/api/chat/stream（同步生成器 StreamingResponse）均 200 正常；端点主体确认运行在 "AnyIO worker thread" 而非事件循环线程；OpenAPI schema 正常生成。

- **位置**：`api/server.py:177`（/api/chat）、:220（/api/ask）、:256（/api/chat/stream）、:284-308（/api/conversations）、:337（/api/vision）、:122（/api/health）
- **问题**：这些 `async def` 端点直接调用阻塞的 LLM/数据库/搜索代码，阻塞整个事件循环——一个慢请求卡住所有并发请求（限流中间件、健康检查同样被卡）。
- **建议**：改为普通 `def` 端点（FastAPI 自动放入线程池），或显式 `run_in_executor`。

### 🔴 14. 并发与线程安全

- **位置**：`src/agent.py:97-101, 355`；`src/mcp/mcp_client.py:18, 63-70`；`src/rate_limiter.py:13-29`
- **问题**：
  - `chat_stream` 按请求调用 `_get_llm(provider)`，`self.llm` 是共享可变状态——两个不同 provider 的并发请求会互相切换对方的模型；
  - `McpClient` 的 `_request_id` 自增和 stdin 写入无锁，而 `ToolRunner` 是并行执行的；
  - `RateLimiter` 无锁（多线程下限额穿透）、`_clients` 的键永不清理（公开服务下内存无界增长）、多 uvicorn worker 时每进程独立计数，实际限额放大 N 倍。
- **建议**：LLM 客户端改为请求级参数传递而非共享可变状态；McpClient 加锁或串行化；限流器加 `threading.Lock` + 定期清理，多 worker 场景改用 Redis 或明确单进程部署约束。

> ✅ **已实施（2026-08-13）**：① `src/agent.py` — LLM 客户端改为请求级参数传递：模块级 `_llm_clients`（provider → client 缓存）+ `threading.Lock`，`_get_llm` 只取缓存、不再替换 `self.llm`；`llm` 参数贯穿 `chat_stream` → `_chat_stream_tools` → `_fallback_rag` / `_generate`（`llm or self.llm` 兜底）。② `src/mcp/mcp_client.py` — 加锁部分已随 §1.1 完成（`self._lock` 包裹 stdin 写入与 `_request_id` 自增）。③ `src/rate_limiter.py` — `threading.Lock` 包裹"检查+记录"（并发下配额不可穿透）；`_cleanup_stale` 定期清理过期/空客户端条目（默认 300s）；docstring 明确单进程部署约束（`main.py` 现为单进程 uvicorn，多 worker 需 Redis）。验证：并发 50 请求仅 3 个放行；4 线程双 provider 并发 120 次流式请求无交叉污染、`self.llm` 未被修改。

### 🔴 15. 数据库错误被静默吞掉

- **位置**：`src/database/postgresql_client.py:174-189`（`_run`）
- **问题**：`_run` 捕获所有异常返回 `[]`，调用方无法区分"无结果"与"数据库故障"：`save_conversation` 失败用户无感知（以为会话已保存），`search_by_keyword` 把错误当空结果再走反向匹配。
- **建议**：返回结构携带 `success/error`（或抛出受控异常），会话保存端点据此返回非 2xx，前端提示"保存失败"。

### 🟡 16. 数据导入不幂等

- **位置**：`src/database/to_postgresql.py:161-170`、`src/database/to_neo4j.py:138-174`
- **问题**：PG 导入用 `if_exists="append"` 且无去重——重复运行导入全部行翻倍；Neo4j 导入用 `CREATE` 且交易 ID 只是行序号（:223 `tx-{i}`），不带 `--clear` 重跑会重复创建交易与关系。
- **建议**：PG 加唯一键 upsert（如 project_code）或导入前检测已有数据；Neo4j 交易用内容哈希做 ID 并 `MERGE`，或强制要求 `--clear`。

> ✅ **已实施（2026-08-13）**：① `src/database/to_postgresql.py` — 新增 `_table_has_rows()`：导入前经 information_schema 检测目标表，已有数据时中止并提示使用 `--drop-first` 或手动清空（表不存在/空表可安全导入）；`--drop-first` 路径不受影响。② `src/database/to_neo4j.py` — 交易 ID 由行序号 `tx-{i}` 改为**行内容 SHA-1 哈希**（新增 `make_transaction_hashes()`，同内容 → 同 ID，与行序无关）；Cypher 中 `CREATE` 全部改为 `MERGE`（Transaction 节点 + HAS_TRANSACTION/PURCHASED_BY/AGENT_BY/LOCATED_AT/SUPPLIED_BY 五类关系），不带 `--clear` 重跑不再重复创建；新增 Transaction.id 唯一约束。注：旧库中 `tx-*` 格式的历史节点需 `--clear` 重建一次方可完全迁移。验证：哈希确定性/内容唯一/行序无关、GBK CSV 加载、`_table_has_rows` 三种分支（mock engine）全部通过；py_compile 通过。
